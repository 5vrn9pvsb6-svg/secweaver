# SecWeaver Agent 升级功能需求

**文档状态：** 本轮差距修复已实施并完成单元/集成回归；不代表已打包或生产发布。  
**内容版本：** `upgrade-requirements-r2`，2026-10-04。  
**适用范围：** 统一 `secweaver-agent` 的定时检查、灰度安装、健康确认和回滚；不改变采集模块的业务逻辑。  
**当前基线：** Agent `0.3.73`；SaaS 受管升级由 Agent Server 的租户策略、活动和设备租约共同决定。

本文件是升级功能的需求基线。它区分当前已经存在的行为与后续需要确认的目标，不能替代发布审批或生产变更授权。模块边界和实现归属见[模块与架构文档](agent-upgrade-architecture.zh-CN.md)。

## 1. 背景与目标

SecWeaver Agent 分布在不同企业、不同 Linux/Windows 主机上。升级必须同时解决四类问题：

1. 只允许可信版本进入主机，防止未签名、篡改或错误平台的二进制被执行。
2. 避免租户开关打开后全量主机同时下载或重启，造成带宽、服务和运维窗口压力。
3. 升级失败时保留可恢复的旧版本，并能根据服务健康结果自动回滚。
4. 让运营人员能够知道“为什么没有升级、现在处于哪一步、下一次何时重试”。

### 1.1 目标

- 提供统一的 Agent 自升级能力，模块进程不拥有替换 Agent 自身的权限和逻辑。
- 默认不自动安装升级；企业必须显式允许，发布人员还必须显式发布目标活动。
- 以不可变 `device_id` 作为灰度身份，支持稳定分组、维护窗口、并发上限和失败熔断。
- 使用 HTTPS、SHA-256 和可选/强制 Ed25519 签名保护清单与二进制。
- 在 Linux systemd 和 Windows SCM 下完成原子替换、重启、健康观察和回滚。
- 把策略拒绝、下载失败、校验失败、安装失败、健康失败和回滚结果写入机器可读状态。

### 1.2 非目标

- 不通过 Agent 持有 SLS 的 AK/SK；Agent 使用设备注册身份和设备密钥协议。
- 不把租户开关当成发布活动；开关只决定该租户是否允许自动安装。
- 不允许普通清单静默降级；回退必须有明确的签名回退指令和服务端策略授权。
- 不把 Agent 自更新与采集模块升级、Logtail/Filebeat 升级混成一个不可回滚事务。
- 不要求客户端在控制面暂时不可达时退出；网络故障只应导致升级延迟并保留重试。
- 不建设独立签名服务或 KMS；复用现有签名工具，由发布运维在受控环境中签名，不取消客户端签名校验。

## 2. 角色与典型流程

| 角色 | 责任 | 不负责的事项 |
|---|---|---|
| 企业 Owner/Admin | 在企业工作台打开或关闭租户自动升级许可 | 不直接上传二进制、不绕过签名校验 |
| 发布运维 | 构建、签名、发布清单，创建升级活动，设置灰度和并发策略 | 不在客户端逐台修改升级资格 |
| Agent Server | 保存租户策略、活动、设备成员、租约和结果；在心跳时做最终授权判断 | 不替代客户端做二进制校验和原子替换 |
| Agent | 定时拉策略、验证清单和物料、执行安装、报告状态、完成健康确认或回滚 | 不自行扩大灰度范围，不在策略关闭时安装 |
| 服务管理器 | 按平台停止/启动 Agent，辅助完成被占用文件的替换 | 不解释升级业务策略 |

典型流程：发布运维准备并签名目标版本 -> 创建租户活动 -> 企业许可打开 -> Agent 心跳取得灰度资格和租约 -> Agent 定时检查并按削峰延迟下载 -> 校验并提交安装 -> systemd/SCM 重启 -> Agent 观察模块健康 -> 上报 `healthy` 或触发回滚。

## 3. 功能需求

### REQ-UPG-001 默认关闭与双重许可

- 新安装配置的 `update.enabled` 和 `update.auto_install` 默认关闭。
- Agent Server 的租户字段 `agent_auto_update_enabled` 默认关闭；关闭时心跳返回 `auto_update_allowed=false` 和 `tenant_auto_update_disabled`，并清理该设备的升级租约。
- 只有企业 Owner/Admin 可以修改租户自动升级许可；不要求二人审批，但每次修改必须写入变更审计，至少记录企业、操作者、旧值、新值、时间、来源请求和结果。
- 租户开关打开仍不等于立即升级；必须同时存在有效活动、目标版本、灰度资格、维护窗口和租约。
- 关闭租户开关、暂停活动或撤销租约后，尚未进入本地提交阶段的安装必须取消或延迟。
- `config set-update --auto-install` 属于管理员显式操作，不能改变生产模板的默认值。

**验收：** 新安装和缺少本地 `update` 块的 Agent 不替换自身；服务端租户开关关闭时，所有设备均记录可解释的拒绝原因。

### REQ-UPG-002 设备身份与灰度稳定性

- 受管升级必须使用注册后不可变的 `device_id`，不得回退到主机名、IP 或临时 PID。
- 同一设备在重启、心跳重试和版本升级后必须落在同一灰度桶。
- 新注册设备不能自动加入已经快照完成的活动成员，除非发布运维显式创建新活动或重建成员快照。

**验收：** 同一 `enterprise_id + device_id + rollout_ring` 的灰度桶稳定；替换/撤销设备不会继承旧设备租约。

### REQ-UPG-003 定时检查、抖动与失败退避

- Agent 按配置周期检查清单；当前模板周期为 6 小时，首次检查延迟 60 秒并加入稳定抖动 300 秒。
- 临时网络、清单或物料错误使用有界指数退避，当前范围为 1 分钟至 1 小时，并遵守 HTTP `Retry-After`。
- 退避和首次抖动必须由设备稳定身份计算，避免重启后所有设备再次同时请求。
- 升级线程必须可取消，不能因为网络请求或下载永久阻塞服务停止。

**验收：** 失败后状态包含 `retryable`、`failure_class` 和 `next_retry_at`；服务停止能在有界时间内结束当前请求。

### REQ-UPG-004 灰度、维护窗口与并发上限

- Agent Server 是 SaaS 受管模式的灰度唯一权威，客户端不再重复解释服务端的成员资格。
- 活动至少支持：通道、目标版本、稳定 ring、成员快照、百分比灰度、维护窗口、最大并发百分比、最大并发设备数、失败样本数和失败率阈值。
- 每个租户可以在企业工作台配置本租户的灰度百分比、最大并发百分比/绝对数、维护窗口和失败熔断阈值；界面保存时必须校验范围，并写入策略变更审计。系统仍保留安全的默认值，租户未配置时不能变成无限并发或全量立即安装。
- 服务端对每个设备签发有过期时间的租约；租约剩余少于 3 分钟时 Agent fail closed。
- 活动达到失败熔断条件时自动暂停，已安装设备仍可完成健康确认，未提交设备不得继续安装。
- standalone 模式可以使用 manifest 自带的 `rollout` 允许/拒绝列表；受管模式清单不得以此绕过服务端资格。

**验收：** 并发上限在并发心跳下仍不被突破；暂停、租约过期和维护窗口关闭均不会进入二进制提交阶段。

### REQ-UPG-005 带宽削峰

- `download_spread_seconds` 只负责已获授权设备的下载延迟，不改变灰度资格。
- 延迟期间如果服务端策略变化、租约过期或设备被暂停，Agent 放弃下载/安装并记录原因。
- 下载必须流式写入受限临时文件，边下载边计算 SHA-256，不把整个包读入内存。

**验收：** 同一活动设备的下载请求在 spread 窗口内分散；取消后临时文件可清理，不产生半包替换。

### REQ-UPG-006 清单、签名与物料完整性

- 清单至少包含 schema、应用名、通道、代次/生成时间、过期时间、目标版本和当前平台物料。
- HTTPS 是默认传输边界；配置可信公钥后必须使用签名信封，不能回退到无签名清单。
- Agent 校验清单签名、清单代次/摘要、平台 URL、文件大小、SHA-256 和二进制签名。
- Windows 正式包还应校验允许的 Authenticode 发布者证书 SHA-256；未配置允许列表的过渡包按兼容规则处理。
- 公钥轮换必须先加入新 key，再在后续签名清单撤销旧 key；不能撤销全部可信 key。
- 私钥只保存在发布环境，不进入 Agent、Operator 包或客户端日志。
- 发布运维保管私钥并使用现有 `cmd/update-sign` 签名；私钥文件仅允许签名操作者读取（Unix 权限 `0600` 或等效 Windows ACL），保留受限访问的加密备份，不提交 Git。CI 负责构建、测试和来源记录，不要求新增签名接口或长期保存发布私钥；Operator 分发已签名物料和公钥，Agent 验签。
- 公钥轮换和全局签名停更由发布运维执行并留发布操作记录。轮换先用当前可信 key 签名加入新公钥，确认适用设备已经信任新 key 后再撤销旧 key；离线设备人工更新信任材料。私钥丢失且无法恢复时必须人工迁移客户端信任，不能自动换 key 冒充原签名者。

**验收：** 篡改清单、未知 key、已撤销 key、过期/回放代次、错误平台、SHA-256 不匹配和签名不匹配均拒绝安装。

### REQ-UPG-007 原子安装与服务生命周期

- 安装前必须取得升级锁、检查磁盘余量、备份当前二进制并持久化恢复标记。
- 提交顺序必须是：下载 -> 校验 -> 备份 -> 写入 `commit_prepared` -> 原子替换/安排替换 -> 写状态。
- 提交一旦开始，策略撤销或上下文取消不能把已经提交的结果伪装为 `policy_deferred`。
- Linux 使用同文件系统原子替换并由 systemd 重启；Windows 不能覆盖运行中的 exe，必须使用同目录待替换文件、受控停止、替换助手和 SCM 重启。
- 升级锁、状态文件、备份和待替换文件必须位于受保护的状态目录；锁应有过期回收机制。

**验收：** 中断发生在提交前时不改变运行二进制；中断发生在提交后时下次启动能识别恢复状态；不允许并发安装或回滚破坏备份。

### REQ-UPG-008 健康观察与自动回滚

- 新版本启动后进入 `installed_pending_health`，默认健康观察窗口为 90 秒。
- 观察期要求所有启用模块持续运行且无影响采集的错误。通常通过新业务输出验证进展；低流量主机没有业务事件时，允许使用采集模块心跳或采集循环健康探测的进展，以及成功的本地 health JSONL 写入作为替代证据，不再强制产生业务事件。
- 替代证据必须来自本次启动后的观察窗口，能证明各启用采集模块仍可工作；仅有父进程存活、通用 Agent 心跳、旧健康记录或云端连接成功不足以判定通过。缺少业务事件不等于模块卡住，缺少可验证的健康进展也不能视为成功。
- 观察器应在健康窗口内主动取得替代证据，不等待常规定时上报周期。模块卡住、探测错误或本地输出写入失败仍导致健康失败；不要求云端收到业务日志，也不为验收伪造安全事件。
- 健康通过后清理恢复标记并保留受限数量的历史备份；当前默认保留 3 份。
- 健康失败时自动恢复前一版本；Linux 和 Windows 都必须上报回滚原因及最终结果。
- 正常人工回滚和远程授权回退必须使用同一锁、备份和原子替换语义。

**验收：** 零业务事件但模块探测及本地健康输出正常的主机通过观察；只有父进程/通用心跳、模块卡住或本地写入失败的主机不能通过。模拟启动失败、健康超时和回滚替换失败，均有可定位状态且不会静默报告成功。

### REQ-UPG-009 可观测性与运维诊断

- 每次检查/安装/回滚输出一条 JSON 状态记录，至少包括状态、原因、当前/目标版本、设备 ID、活动 ID、策略版本、清单代次/摘要和重试信息。
- 必须能区分：策略拒绝、租户关闭、灰度外、租约不足、清单失败、下载失败、校验失败、备份失败、替换失败、服务失败、健康失败和回滚失败。
- `doctor`、健康 JSONL 和服务日志应反映升级状态；不得把“本地 JSONL 已生成”误报成“云端已到达”。
- 日志中禁止输出 enrollment token、私钥、完整授权头和敏感 URL 参数。

**验收：** 只查看状态文件和日志即可回答当前版本、目标版本、当前阶段、最近失败原因和下次重试时间。

### REQ-UPG-010 兼容、私有化和离线边界

- **兼容责任在 Agent Server：** SaaS 服务端必须向后兼容支持范围内的历史 Agent 版本和协议。客户主机上的 Agent 可以长期处于不同版本，服务端发布不能以客户同步升级为前提。
- 保留旧 Agent 的注册、心跳、升级策略和状态上报契约；新增请求字段不能变成旧协议的必填项，已有字段不能静默改变类型或含义。服务端按协议和已验证能力返回响应，未知能力不能仅凭版本号推断为已支持。
- 租户许可始终在服务端判定。旧 Agent 即使不识别 `auto_update_allowed`，服务端也必须使用该客户端已支持的禁用契约，例如 `enabled=false`、无资格/不发租约，阻止受管自动升级；不能只依靠一个旧客户端不认识的新字段。
- 缺少关键安全能力的旧 Agent 不应获得不安全的升级许可。服务端应暂停其受管自动升级并提供兼容路径或人工升级建议，同时继续支持其既有注册、心跳和正常采集，不因新增升级协议中断这些功能；兼容不豁免原有认证和授权。
- 不设置“一个服务端发布周期后要求全部客户端升级”的期限。历史协议退出支持时需独立兼容政策、提前通知和迁移路径，另行确认。现有新 Agent 对旧服务端缺字段的容错只是实现现状，不是本项 SaaS 兼容需求的主体。
- SLS SaaS 使用 Agent Gateway 的设备心跳/策略接口；私有化和 ES 模式可使用独立 HTTPS manifest 与本地公钥，不依赖 SaaS 源码。
- 完全离线环境暂时只支持人工执行 `secweaver-agent update install`；不部署本地活动服务，不提供无人值守的离线自动升级。安装命令仍必须使用本地可信清单、公钥和物料，不能隐式访问公网。
- Linux 支持 systemd 发行版；Windows 支持 SCM 服务。非 systemd Linux 或缺少 Windows 服务权限时，安装器必须明确报告不支持原因。

**验收：** 新 Agent Server 同时通过受支持新旧 Agent 的注册、心跳、租户关闭、策略和状态上报契约测试；缺新字段的旧客户端不被拒绝或误报升级成功，缺安全能力时只延迟受管升级。私有 CA、离线清单、Linux systemd 和 Windows SCM 有对应验证，不把兼容降级误报为强安全模式。

## 4. 状态模型

客户端状态至少使用以下阶段：

```text
disabled
  -> policy_deferred
  -> checked
  -> update_available
  -> download_delayed
  -> downloaded_verified
  -> commit_prepared
  -> installed_pending_health
  -> healthy

任一阶段 -> failed
failed/health_failed -> rollback_scheduled|rolled_back|rollback_failed
```

`policy_deferred` 不是错误成功，而是明确表示当前没有执行资格；`failed` 必须配合失败分类和是否可重试；`healthy` 只在观察期完成后产生。

## 5. 配置与接口要求

### 5.1 Agent `update` 配置

```json
{
  "update": {
    "enabled": false,
    "channel": "stable",
    "interval_seconds": 21600,
    "initial_delay_seconds": 60,
    "jitter_seconds": 300,
    "retry_initial_seconds": 60,
    "retry_max_seconds": 3600,
    "auto_install": false,
    "require_server_policy": true,
    "health_timeout_seconds": 90,
    "lock_stale_seconds": 3600,
    "max_backups": 3,
    "min_free_space_mb": 256
  }
}
```

`auto_install=false` 表示可以检查但不替换；`require_server_policy=true` 表示安装还要等待服务端心跳策略。生产配置还必须配置 HTTPS manifest、CA（如私有 CA）和可信 Ed25519 公钥。

### 5.2 服务端 `update_policy`

服务端策略至少包含 `campaign_id`、`policy_revision`、`target_version`、`channel`、`manifest_url`、`rollout_percentage`、`auto_install`、`paused`、维护窗口、并发上限、失败熔断参数和 `allow_downgrade/rollback_reason`。设备响应还应包含 `eligible`、`lease_granted`、`lease_expires_at`、`reason` 与 `auto_update_allowed`。

### 5.3 本地状态

`state.json` 是恢复依据，不是展示缓存；至少保存当前/前一/目标版本、尝试 ID、活动 ID、策略版本、清单代次/摘要、备份路径、待替换路径、健康窗口、失败分类和下次重试时间。任何写状态失败都必须保留恢复材料并在下一次启动重新判断。

## 6. 验收矩阵

| 验收项 | 证据 |
|---|---|
| 默认不升级 | 新安装配置、`doctor` 和定时状态显示关闭原因 |
| 租户关停生效 | Agent Server 策略测试返回 `tenant_auto_update_disabled`，不发租约 |
| 灰度稳定 | 同一设备重复心跳得到同一资格；并发测试不突破上限 |
| 削峰有效 | spread 窗口内下载时间分散，策略变化可取消 |
| 供应链安全 | 签名、代次、SHA-256、平台和 Windows Authenticode 负例均拒绝 |
| 服务可恢复 | Linux systemd、Windows SCM 的正常升级、零业务事件下健康通过、模块卡住/健康输出失败下拒绝通过、启动失败、健康超时和回滚 |
| 网络故障可恢复 | Agent 不退出，按退避重试，恢复后继续心跳/检查 |
| 可诊断 | 状态 JSONL、health 日志、doctor 能定位阶段和原因 |
| 兼容与离线 | 新服务端对新旧 Agent 的契约测试；租户关闭时旧 Agent 也不能获得升级许可；私有 CA、本地 manifest 和无公网环境有明确结果 |

## 7. 已确认决策与待确认事项

已确认规则与实施结果如下：

1. 租户开关只允许 Owner/Admin 修改；不需要二人审批，但每次修改必须变更审计。
2. 灰度、最大并发、维护窗口和失败熔断参数由每个租户在企业工作台配置；平台提供安全默认值和范围校验。新租户默认灰度 `10%`、最大并发 `10` 台、失败率 `20%`、最小样本 `1`，维护窗口必须保存为全天或具体时段。
3. 已确认：Agent Server 是 SaaS 服务端，必须兼容部署在客户机器上的不同 Agent 版本；不要求客户与服务端同步升级。具体支持版本清单和历史协议退出政策需通过契约测试和独立兼容政策确定。
4. 已确认简化：不建设签名服务/KMS。发布运维在受控环境保管私钥，使用现有工具签名、轮换和紧急停更；CI 构建/测试并生成 provenance，Operator 分发已签名物料与公钥，Agent 验签；企业工作台不接触发布私钥。
5. 已确认：低流量主机允许“所有模块持续运行 + 可验证的模块健康进展/health JSONL 持续推进 + 无影响采集的错误”作为通过证据，不要求业务事件产生；不能仅以父进程存活或通用心跳代替采集模块健康。
6. 完全离线部署已确定暂时只支持人工 `update install`，不建设本地活动服务。

**既有确认记录：** 对话中已确认无需二人审批但需要审计、按租户配置升级参数和离线仅人工升级；2026-10-04 用户明确服务端兼容方向、允许第 5 项健康替代证据，并要求“第四点简化，不建设签名服务/KMS”。这些选择不等于对后续新增接口、参数和探测方式的批准。

## 8. 本轮差距修复范围

**确认来源：** 2026-10-04，用户在逐项代码差距分析后回复“好的，按照你的建议来修复”。本次确认以下修复目标，不扩展为对尚未提出的详细架构、生产操作或未来功能的批准。

| 修复目标 | 需求归属 | 完成条件 |
|---|---|---|
| 统一事务锁和恢复状态 | REQ-UPG-007/008 | 锁/检查失败或并发确认不能覆盖另一安装/回滚的恢复状态 |
| 恢复独立于定时开关 | REQ-UPG-008/010 | 关闭定时更新的人工升级仍健康确认/回滚，不访问远程源 |
| 低流量健康证据 | REQ-UPG-008 | 各采集循环有新进展且本地健康写入成功；零事件可通过，卡住/旧证据不能通过 |
| 调度/退避/削峰 | REQ-UPG-003/005 | 相同续租不重置等待，撤销取消提交前操作，尊重 Retry-After |
| 租户完整策略 | REQ-UPG-004 | 工作台配置灰度/并发/窗口/熔断，验证权限、校验、审计、隔离 |
| 旧 Agent 安全兼容 | REQ-UPG-010 | 未验证能力只延迟升级，不中断支持范围内注册/心跳/采集或放宽认证 |

| 安装默认一致 | REQ-UPG-001 | 默认不开本地检查/安装，显式启用及关闭原因可诊断 |
| 审计/可观测性 | REQ-UPG-001/009 | 审计旧/新值和请求结果，doctor/health/日志/心跳投影同一结果 |

**范围：** Community Agent、独立 Agent Server 和独立 SaaS Server 工作台；必要的模块健康接口、兼容字段和增量迁移需先确认架构。不改变安全事件分类/过滤，不合并 shipper 升级，不维护旧仓库内的独立项目副本。

**不包含：** 打包上传、生产迁移/部署、私钥创建/轮换、离线活动服务或签名服务/KMS。后续变更 Agent 包递增不可变版本，Server/Operator 保持独立版本。

**实施说明：** 具体默认值、低流量模块健康证据、旧 Agent 能力兼容和租户偏好约束已按[架构第 11 节](agent-upgrade-architecture.zh-CN.md#11-本轮修复设计已实施)实现。仍需在发布前完成版本递增、制品构建、数据库迁移演练和生产验证。
